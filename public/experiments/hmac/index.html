Objective

HMAC Authentication and Verification

The objective of this laboratory experiment is to understand, implement, and analyze the mathematical structure and cryptographic properties of Keyed-Hash Message Authentication Codes (HMAC) as defined in RFC 2104 and NIST FIPS PUB 198-1.

Core Learning Objectives:
  • Understand why simple unkeyed hash functions (like raw SHA-256) and naive concatenation Hash(Key || Message) fail to protect against length-extension and spoofing attacks.
  • Trace the RFC 2104 nested two-pass construction using the derived key K', inner pad constant ipad (0x36), and outer pad constant opad (0x5C).
  • Simulate message transmission across an untrusted network and observe how unauthorized message tampering or key mismatch leads to immediate verification failure.
  • Analyze the Avalanche Effect by quantifying bit-level Hamming distances between digests when altering single characters in the message or secret key.
  • Distinguish the operational boundaries between encryption (confidentiality) and HMAC (integrity and authenticity).
Theory

Cryptographic Theory & RFC 2104 Construction

1. What is an HMAC?

A Keyed-Hash Message Authentication Code (HMAC) is a specific construction for calculating a message authentication code involving a cryptographic hash function in combination with a shared secret key. It verifies both data integrity and the authenticity of a message.

2. The RFC 2104 Mathematical Specification

Let H denote the underlying cryptographic hash function (such as SHA-256), B denote the block length of the hash function in bytes (64 bytes for SHA-256), and L denote the hash output length in bytes (32 bytes / 256 bits for SHA-256).

HMAC(K, m) = H((K' ⊕ opad) ∥ H((K' ⊕ ipad) ∥ m))

The components of the formula operate as follows:

  • Derived Key (K'): If the shared secret key K is longer than block size B (64 bytes), it is hashed first: K' = H(K). If K is shorter than B, it is padded with zeroes on the right up to B bytes.
  • Inner Pad (ipad): The constant byte 0x36 repeated B (64) times.
  • Outer Pad (opad): The constant byte 0x5C repeated B (64) times.
  • ⊕: Bitwise Exclusive-OR (XOR) operation.
  • ∥: Data concatenation.

3. Why Not Just Hash H(Key ∥ Message)?

A naive approach to message authentication would be computing H(Key ∥ Message). However, for iterated hash functions based on the Merkle-Damgård construction (such as MD5, SHA-1, SHA-256, and SHA-512), this naive concatenation is severely vulnerable to Length Extension Attacks.

In a length extension attack, an attacker who observes the digest H(Key ∥ Message) and knows the length of the original message can reconstruct the internal compression state of the hash function, append arbitrary malicious data, and compute a valid digest for the extended message without knowing the secret key.

The nested two-pass design of HMAC completely prevents length extension attacks because the inner hash output is wrapped and re-hashed with the outer padded key: H((K' ⊕ opad) ∥ inner_hash).

4. The Avalanche Effect

Due to the diffusion and confusion properties of SHA-256, HMAC exhibits a strong Avalanche Effect: changing even a single bit in the message or secret key causes approximately 50% of the output bits to flip pseudorandomly.

5. Can HMAC Be Decrypted?

A common misconception is asking whether an HMAC tag can be decrypted to recover the message. The answer is NO. HMAC is a one-way mathematical digest that losslessly compresses arbitrary-length inputs into a fixed 256-bit tag. It is not an encryption cipher. To achieve both confidentiality and integrity, modern cryptographic protocols employ the Encrypt-then-MAC paradigm (e.g., AES-256-CBC followed by HMAC-SHA-256).

Procedure

Laboratory Procedure

Follow these steps to conduct the virtual laboratory simulation:

  1. HMAC Generation:
    • Enter your plaintext message in the Message field (or click Load RFC 2104 Preset).
    • Enter a shared secret key in the Secret Key field.
    • Click Generate HMAC Tag to compute the 64-character hexadecimal HMAC-SHA-256 tag.
    • Observe the intermediate derived key K', the inner padded key (K' ⊕ ipad), and the outer padded key (K' ⊕ opad).
  2. In-Transit Network Simulation:
    • Click Send Packet to Channel to transmit the packet containing the message, key, and HMAC tag across the simulated network channel.
    • Click Tamper Message to alter a character in the transmission, or click Tamper Key to simulate key mismatch.
    • Observe how the channel flags the modification.
  3. Verification at Receiver:
    • Click Verify HMAC Authenticity on the receiver card.
    • The receiver recalculates the HMAC using the received message and received key, then compares it against the transmitted tag.
    • Inspect the verification verdict: green for successful match (data authentic), or red for verification failure (tampering detected).
  4. Avalanche Effect Analysis:
    • Switch to the Avalanche Effect tab.
    • Click Flip 1 Bit in Message and click Compute Avalanche Analysis.
    • Review the bit-difference count (Hamming distance) and the percentage of flipped output bits.
  5. Self-Assessment Quiz:
    • Switch to the Knowledge Quiz tab.
    • Answer all 10 multiple-choice questions and click Submit Answers to test your mastery of HMAC theory and security mechanisms.
