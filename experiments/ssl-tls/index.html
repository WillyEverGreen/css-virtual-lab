Section 1

SSL/TLS Protocol Overview & Handshake Analysis

The primary objective of this laboratory experiment is to study and simulate the fundamental architecture, key agreement mechanisms, and message sequencing of the Transport Layer Security (TLS 1.2 & TLS 1.3) protocols. Students will investigate the difference in round-trip latency between TLS 1.2 (2-RTT) and TLS 1.3 (1-RTT), observe how Perfect Forward Secrecy (PFS) is achieved via Ephemeral Diffie-Hellman (ECDHE P-256) key exchanges, verify digital certificates to defend against Man-in-the-Middle (MITM) attacks, and inspect encrypted application record exchange using authenticated AEAD symmetric ciphers (AES-GCM).

Experiment Aim

Standardized in RFC 8446 (TLS 1.3) and previously in RFC 5246 (TLS 1.2), TLS provides confidentiality, integrity, and authentication through a synergy of asymmetric key exchange, X.509 digital certificates, and authenticated symmetric encryption. TLS 1.3 deprecates insecure legacy ciphers (static RSA key transport, CBC padding mode, RC4, 3DES) and reduces connection latency to a single round trip (1-RTT).

1. Handshake Protocol

Negotiates cipher suites, authenticates the server identity via digital certificates, and securely establishes shared symmetric keys in 1 RTT.

2. Perfect Forward Secrecy

Mandates Ephemeral Diffie-Hellman (ECDHE) so that future compromise of the server's private key cannot decrypt past recorded sessions.

3. AEAD Record Encryption

Wraps all application data in Authenticated Encryption (AES-GCM), eliminating legacy padding oracle attacks (POODLE, Lucky 13, BEAST).

Section 2

Cryptographic Architecture & Protocol Layers

TLS operates as a layered protocol positioned between the Transport layer (TCP) and the Application layer (e.g., HTTP). It provides confidentiality, integrity, and authentication through a synergy of asymmetric key exchange, X.509 digital certificates, and authenticated symmetric encryption.

1. The Subprotocol Hierarchy

Handshake Protocol

Negotiates protocol version, cipher suites, exchanges random nonces, performs public key exchange, and authenticates peer certificates.

Record Protocol

Secures application data using keys from the handshake. It fragments, authenticates, and encrypts payloads before transmission.

Alert Protocol

Transmits warnings and fatal errors (e.g. bad_certificate, bad_record_mac, handshake_failure). Fatal alerts immediately terminate the connection.

2. Ephemeral Diffie-Hellman (ECDHE) Key Exchange

In TLS 1.3, static RSA key transport is eliminated. Both client and server dynamically generate ephemeral key pairs on NIST curve P-256 (secp256r1):

Ephemeral Diffie–Hellman Key Exchange (ECDHE): Client: Qc = dc × G  |  Server: Qs = ds × G  |  Shared Secret: Z = dc × Qs = ds × Qc = (dc × ds) × G
Perfect Forward Secrecy Guarantee

Because private keys d_c and d_s are discarded immediately after the session finishes, Perfect Forward Secrecy (PFS) is guaranteed: an adversary intercepting and recording ciphertext cannot decrypt historic conversations even if they later compromise the server's long-term certificate private key.

3. Key Derivation & Master Secret

Using the HMAC-based Key Derivation Function (HKDF in TLS 1.3 / PRF in TLS 1.2), the client and server combine nonces and the shared secret Z to derive:

  • Client Write Key & IV: Encrypts outbound data from client to server.
  • Server Write Key & IV: Encrypts outbound data from server to client.
  • Finished MAC Keys: Authenticates the complete transcript of prior handshake messages to defeat tampering.

4. TLS 1.2 vs TLS 1.3 Architectural Comparison

Feature TLS 1.2 (RFC 5246) TLS 1.3 (RFC 8446) Security & Performance Impact
Handshake Latency 2 Round Trips (2-RTT) 1 Round Trip (1-RTT) + 0-RTT Resumption 50% latency reduction in initial TCP connection establishment
Key Exchange Static RSA, DHE, or ECDHE ECDHE exclusively mandated Guarantees Perfect Forward Secrecy; eliminates retrospective decryption
Cipher Suite Architecture Over 30 legacy suites; separate auth/cipher/hash 5 streamlined AEAD suites (e.g. TLS_AES_128_GCM_SHA256) Drastically shrinks attack surface and configuration error potential
Symmetric Ciphers CBC mode with HMAC, RC4, 3DES, AES-GCM AEAD only (AES-GCM, AES-CCM, ChaCha20-Poly1305) Eliminates padding oracle attacks (POODLE, Lucky 13, BEAST)
Certificate Privacy Transmitted in cleartext during handshake Encrypted using derived handshake secret Prevents passive eavesdroppers from observing host identity
Section 3

Laboratory Procedure

Follow these experimental steps to evaluate the TLS handshake state machine:

  1. Configuration: Navigate to the Simulator tab. Select protocol version (TLS 1.3 or 1.2), key exchange algorithm (ECDHE or RSA), and execution scenario (Normal, Expired Certificate, MITM Forged Cert, or Tampered Finished Message).
  2. Run Handshake: Click Play Auto-Run to watch the live animated packet flight across the network channel, or click Step Forward to advance through the protocol messages one by one.
  3. Packet Inspection: Click any message packet in the central network channel to examine its structured JSON payload (protocol version, randoms, cipher suites, key shares, or verification tags) in the Packet Inspector.
  4. Application Data Exchange: Once the handshake completes with status Established, enter a plaintext application message in the Client terminal and click Send Encrypted Record. Observe AES-GCM ciphertext transmission and automatic server-side decryption.
  5. Attack Scenarios & Alerts: Test the failure scenarios (Expired Certificate, MITM Attacker, Tampered MAC) to observe how TLS triggers fatal alerts and terminates the session without exposing application data.
