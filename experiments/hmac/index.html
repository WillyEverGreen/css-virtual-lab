Section 1

HMAC Authentication and Verification

The objective of this laboratory experiment is to understand, implement, and analyze the mathematical structure and cryptographic properties of Keyed-Hash Message Authentication Codes (HMAC) as defined in RFC 2104 and NIST FIPS PUB 198-1.

Experiment Aim
  • Understand why simple unkeyed hash functions and naive concatenation Hash(Key || Message) fail to protect against length-extension and spoofing attacks.
  • Trace the RFC 2104 nested two-pass construction using the derived key K', inner pad constant ipad (0x36), and outer pad constant opad (0x5C).
  • Simulate message transmission across an untrusted network and observe how unauthorized tampering or key mismatch leads to immediate verification failure.
  • Analyze the Avalanche Effect by quantifying bit-level Hamming distances between digests when altering single characters in the message or secret key.

1. Data Integrity

Detects any unauthorized modification, insertion, or alteration of the message payload M during transit over an untrusted channel.

2. Origin Authentication

Proves the transmitted message was generated by a legitimate party holding the shared secret key K, not by a forging adversary.

3. Forgery Resistance

An attacker cannot compute a valid HMAC tag without knowing K, even after observing many authentic message-tag pairs.

Section 2

Cryptographic Theory & RFC 2104 Construction

1. What is an HMAC?

A Keyed-Hash Message Authentication Code (HMAC) is a specific construction for calculating a message authentication code involving a cryptographic hash function in combination with a shared secret key. It verifies both data integrity and the authenticity of a message.

2. The RFC 2104 Mathematical Specification

Let H denote the underlying cryptographic hash function (such as SHA-256), B denote the block length of the hash function in bytes (64 bytes for SHA-256), and L denote the hash output length in bytes (32 bytes / 256 bits for SHA-256).

HMAC Mathematical Construction (RFC 2104): HMAC(K, m) = H((K' ⊕ opad) ∥ H((K' ⊕ ipad) ∥ m))

The components of the formula operate as follows:

  • Derived Key (K'): If the shared secret key K is longer than block size B (64 bytes), it is hashed first: K' = H(K). If K is shorter than B, it is padded with zeroes on the right up to B bytes.
  • Inner Pad (ipad): The constant byte 0x36 repeated B (64) times.
  • Outer Pad (opad): The constant byte 0x5C repeated B (64) times.
  • ⊕ : Bitwise Exclusive-OR (XOR) operation.
  • ∥ : Data concatenation.
Parameter Symbol Standard Value (SHA-256) Operational Description
Block Size B 64 bytes (512 bits) Input block boundary of the underlying compression function
Output Length L 32 bytes (256 bits) Fixed output digest size generated by SHA-256
Inner Pad Constant ipad 0x36 (repeated 64 times) Bitwise XORed with K' to initialize the inner hash stream
Outer Pad Constant opad 0x5C (repeated 64 times) Bitwise XORed with K' to initialize the outer re-hash pass

3. Why Not Just Hash H(Key ∥ Message)?

Length Extension Attack Vulnerability

For iterated hash functions based on the Merkle-Damgard construction (MD5, SHA-1, SHA-256, SHA-512), naive key-prefix concatenation H(Key ∥ Message) is severely vulnerable to Length Extension Attacks.

In a length extension attack, an attacker who observes the digest H(Key ∥ Message) and knows the length of the original message can reconstruct the internal compression state of the hash function, append arbitrary malicious data, and compute a valid digest for the extended message without knowing the secret key.

The nested two-pass design of HMAC completely prevents this because the inner hash output is wrapped and re-hashed with the outer padded key: H((K' ⊕ opad) ∥ inner_hash).

4. The Avalanche Effect

Due to the diffusion and confusion properties of SHA-256, HMAC exhibits a strong Avalanche Effect: changing even a single bit in the message or secret key causes approximately 50% of the output bits to flip pseudorandomly.

5. Can HMAC Be Decrypted?

Common Misconception
HMAC is a one-way mathematical digest that losslessly compresses arbitrary-length inputs into a fixed 256-bit tag. It is not an encryption cipher: it cannot be decrypted to recover the message. To achieve both confidentiality and integrity, modern protocols use the Encrypt-then-MAC paradigm (e.g., AES-256-CBC followed by HMAC-SHA-256).
Section 3

Laboratory Procedure

Follow these steps to conduct the virtual laboratory simulation:

  1. HMAC Generation: Enter your plaintext message and shared secret key, then click Generate HMAC Tag. Observe the computed 64-character HMAC-SHA-256 hex digest and the intermediate derived key K', inner padded key, and outer padded key.
  2. Network Transmission & Tamper Simulation: Click Send Packet to Channel to transmit the packet. Use Tamper Message or Tamper Key to simulate an in-transit attack and observe how the channel flags the modification.
  3. Verification at Receiver (Bob): Click Verify HMAC Authenticity. Bob recalculates the HMAC using the received message and key, then compares against the transmitted tag. Green indicates authentic, Red indicates tampered.
  4. Avalanche Effect Analysis: Switch to the Avalanche Effect tab. Click Flip 1 Character and run Compute Avalanche Analysis to measure the Hamming distance and percentage of flipped output bits (expected: ~50%).
  5. Self-Assessment Quiz: Switch to the Knowledge Quiz tab. Answer all 10 multiple-choice questions and click Submit Answers to test your mastery of HMAC theory and security mechanisms.
  6. RFC 2104 Mathematical Trace: Inspect the Step-by-Step Mathematical State Trace below the generator. Read the derived key K', inner padded key XOR values, inner hash, and the final HMAC digest at each stage.
